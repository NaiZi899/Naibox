# 系统提示词

网关在**出站前**改写请求体里的 `system` / `developer` 消息。这件事解决的不是"让模型听话"，
而是**一个具体的误杀**：客户端（Claude Code / Codex 之类）会在 system 里注入若干固定模板句，
上游内容审核对这些句子做**逐字精确匹配**，命中就整单拦截。于是一批完全合法的流量被拒，
而用户看到的只是一次 400。

## 三层分工

| 层 | 位置 | 管什么 | 不管什么 |
|---|---|---|---|
| 提示词层 | `internal/prompt` | system / developer 消息里的指纹 | user / assistant / tool 消息 |
| 脱敏层 | `internal/wire`（sanitize） | 所有消息里的已知指纹串 | 来源性（它只擦，不换人格） |
| 防护层 | `internal/prompt/gate.go` | 撞过审核之后的重试形态 | 事前预防 |

两层并存不是冗余：提示词层从**源头**消灭 system 来源的模板句；脱敏层兜住用户自己粘贴的日志、
assistant 历史与工具参数。关掉任一层都会留下一个明确的缺口。

## 三种模式

| 模式 | 未降级时 | 降级中（见下） |
|---|---|---|
| `custom`（默认） | 删掉客户端全部 system/developer，插入网关自有提示词 | 整段换成中性提示词 |
| `append` | **保留**客户端 system/developer，在其后追加一条网关 system | 同样整段换成中性提示词 |
| `passthrough` | 原样透传，一个字节都不动 | 同样整段换成中性提示词 |

- `custom` 最能消指纹，代价是丢掉客户端自己的 system（工程约定、工具说明）。
- `append` 保住客户端人格，代价是客户端那段模板句**仍然在请求里** —— 只能靠追加的那段
  改写认知 + 脱敏层兜底，**不保证不误杀**。另外"两段人格并存"本身会让模型在冲突指令间摇摆，
  且 token 成本翻倍。
- `passthrough` 完全不动，撞上审核时由降级机制兜一次。

`append` 是**幂等**的：同一个提示词已经在 system 里（content 完全相等）就不再插，
所以重试、降级重放、上层二次包装都不会让同一条指令出现三次。

## 降级机制（以及它的代价）

降级状态机 `prompt.Gate`：某次请求被上游内容拦截 → `Trigger()` → 在 CST 自然日结束前，
所有请求的 system 都换成 `prompt.Degraded`（一句极简中性话）→ 同一请求内重试一次。

**这是设计上的取舍，不是缺陷**：降级期的目标是"尽可能不带指纹的文本"，而 `append` /
`passthrough` 保留的客户端 system 恰恰是一分钟前刚被拒的那段，继续送只会再撞一次。
所以三种模式在降级期**没有区别**。

代价也很明确：如果注入的是"能力向"提示词（例如让模型更少拒绝、更直接输出），
降级触发后**这层能力会整个消失**，直到状态机自然日重置。需要"降级期也保留一部分"时，
正确做法是让降级文本可配置，而不是让降级期继续送客户端 system。

## 配置

```json
"prompt": {
  "mode": "custom",
  "file": ""
}
```

| 键 | 说明 |
|---|---|
| `prompt.mode` | `custom` / `append` / `passthrough`；空值按 `custom` 处理；其它值**启动即失败** |
| `prompt.file` | 人格文件路径。留空 = 用内置默认（`internal/prompt/defaultprompt.md`，约 2KB） |

`prompt.file` 非空但**不可读或为空**时启动直接失败 —— 这是一个几乎必然是配置错误的状态，
静默回落内置默认会让"我的人格为什么不生效"变成一场无信号的排查。

### 回滚通道

```
NAIBOX_PROMPT_MODE=passthrough
```

环境变量优先于 `config.json`（在 `applyEnv` 阶段生效，早于模式校验），所以拼错的值也不会
把进程卡住。用途只有一个：现场止血时把提示词层瞬间关掉，不必改配置、不必重启面板。
非法值会被忽略并打一条日志，不会阻断启动。

## 管理台

**设置 → 系统提示词**（带「重启生效」徽标）。改完保存后需要重启进程才生效 ——
这是刻意的：`applyToMemory` 只写配置意图，**不**重载运行中的提示词正文，否则会出现
"界面显示已生效、实际出站还在用旧词"这种更难查的状态。

只读状态行（`prompt_status`）说明当前**真正在用**的那份：

| 字段 | 含义 |
|---|---|
| `mode` | 当前生效模式（启动时算出的值，不是配置里待生效的值） |
| `source` | `builtin`，或 `file:<路径>` |
| `bytes` | 生效提示词正文字节数 |
| `degraded_until` | 降级中才有值（RFC3339）；未降级为空串 |
| `scope` | 生效范围，当前固定 `workbuddy` |

### 保存时就会被拦住的三件事

1. 模式不在三值之内（含空串被显式提交）；
2. `file` 非空但文件不可读 / 为空 —— 判据复用 `prompt.Load`，与启动期同源，避免"保存通过、重启起不来"；
3. 正文命中脱敏指纹串 —— 这类文本注入后仍会被 sanitize 改写（例如裸 `11128` 变 `11-128`），
   界面上看到的与上游实际收到的不是同一份。**`passthrough` 除外**：它不发出这段文本，
   且是回滚通道的落点，两者口径必须与启动期一致。

任一条不通过都**不写盘**，`config.json` 保持原样，错误文案会指明原因。

启动期同样会查这三件事，区别只有一处：**`passthrough` 下的指纹只警告不阻断** ——
它根本不会把这段文本发出去（文件只被校验、不被使用），而它同时是上面那条回滚通道的落点，
在这里 fail fast 等于把唯一的救火通道焊死。

## 生效范围

当前只覆盖 **WorkBuddy（默认上游）**那条出站客户端。其它上游（loomy / trae / codearts /
jiyuan / inkstone / qoder / cline / raccoon / lobsterai / workbuddy_intl）不走这段逻辑，
它们的指纹问题仍由 `internal/wire` 的脱敏层处理。

## 排障

| 现象 | 先看 |
|---|---|
| 配了 `append` 但感觉没生效 | 启动日志 `系统提示词：mode=… 来源=…（N 字节）` |
| 界面写"降级中（至 …）" | 说明刚撞过上游内容拦截，等到该时刻后自动解除 |
| 保存被拒 | 设置页错误文案会指明是模式 / 文件 / 指纹哪一条 |
| 提示词里明明写了 X，上游收到的却是 Y | 正文命中了脱敏指纹表，被 sanitize 改写；改成不含指纹的措辞 |
| 启动时报 `prompt.mode=… 非法` | `config.json` 或 `NAIBOX_PROMPT_MODE` 的取值不在三值内 |
